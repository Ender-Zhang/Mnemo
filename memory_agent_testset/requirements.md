# GUI Agent 记忆/事件利用能力 —— 测试集需求与设计框架

> 本文件记录需求与设计约定,方便下次继续扩充或调整。数据文件见 `testset_v2.json`。

## 1. 目标

生产测试数据,评测一个 **GUI Agent 利用历史事件(过去做过的任务与交互)来完成新任务的能力**,难度由浅到深。

- **输入** = 一条新的「用户指令」 + 一组「历史事件」(过去做过的任务/交互记录)。
- **期望输出** = Agent 应该执行的行为(选择/筛选/排除),以及背后的推理。

## 2. 关键概念修正:事件(events),而非「记忆」

之前用的「记忆」太干净(已经替用户提炼好了偏好),不真实。改成 **事件 events**:

- 事件是 **原始的过去任务/交互记录**,不是提炼好的偏好结论。
- 一组事件里 **可以有冲突、冗余、干扰项**。
- 有的事件可以 **直接复用用户当时的选择**;有的需要 Agent **自己推理/泛化/排除**。
- Agent 的能力恰恰体现在:从一堆杂乱事件里,判断哪些相关、如何去重、如何解决冲突、该不该用、要不要泛化。

### 2.1 事件必须是「原子记录」,不能是「偏好结论」(最重要)

事件 = **一次具体发生过的行为/交互**,带具体属性(品牌、型号、价格、座位、位置、菜品、数量、被放弃的候选项、退货/取消/差评等),并带时间戳。**不要使用「偏好/一向/总是/喜欢/习惯」这类已经替用户总结好的结论词**——那等于把答案直接喂给 Agent,推理步骤就被跳过了。

- ❌ 错误(结论):`用户一向偏好戴森等高端品牌,小家电多是高端款。`
- ✅ 正确(原子事件,需多条):
  - `2025-03-20,买了戴森 V12 吸尘器,3990 元。`
  - `2025-09-14,买了戴森吹风机,2990 元。`
  - `2026-01-08,买电压力锅时,在 399 元入门款和 1899 元高端款里选了 1899 元的。`
  - → Agent 自己推断出「小家电偏高端」,再泛化到电饭煲。

要点:
- **多条原子事件 > 一条总结**。一个稳定偏好通常要 2~3 条同向事件才能立住(也便于制造冗余/冲突)。
- **揭示性选择最有价值**:记录「在候选 A/B 里选了谁、放弃了更便宜/更近/更多设施的哪个」,偏好从取舍中自然显现。
- **行为信号**:退货、取消改单、差评、备注,都是可推断的原子事件。
### 2.2 事件 = GUI 操作痕迹,**绝不含反馈/结果/主观感受**(同等重要)

事件就是「用户上一次用 GUI agent 操控时被记录下来的操作历史」,例如「点了麦当劳麻辣鸡腿堡套餐,可乐选了不加冰」。GUI agent 只能观测到**用户的操作**,观测不到吃没吃完、好不好吃、身体反应、他人评价。因此事件里**不能出现任何反馈/结果/主观感受**。

**粒度:写成「选择的总结」,不是按钮级操作,也不是偏好结论。** 三档对照:
- 太细(按钮级,❌):`在筛选里勾选了「距地铁500米内」,对该订单点了申请退款`
- 太高(结论,❌):`偏好靠窗` / `一向住近地铁`
- 刚好(选择总结,✅):`选了靠窗的座位` / `点奶茶选了少糖` / `订了离地铁近的酒店` / `退了那一单`
保留有意义的选择内容(品牌、价位档、选了什么、放弃了哪个候选),去掉 UI 机械细节(座位排号、航班代码、「勾选/对订单申请」等动词)。

允许出现的(可观测操作 / 客观数据):
- 下单、预订、购买(含品牌/型号/价格/座位/选项/定制/备注)
- 在候选 A/B 间选了谁、放弃了哪个(揭示性选择)
- 筛选/搜索(勾选了什么条件)、领券、改地址、改资料
- **取消、退货/退款、退卡、转卖、改单、换一家下单**(负向信号只能来自这些操作)
- 下单的时间分布、账户数据(里程余额)、日历日程、商品页标注、系统当前状态(某店已下线)

禁止出现的(observation 不到):
- 结果:`基本吃完没剩多少`、`没赶上航班损失全款`、`血糖升高`、`高原反应`、`喊冷`
- 主观感受/评价:`很喜欢`、`满意`、`抱怨隔音差`、`打了 2 星`、`好吃/难吃`、`后悔`
- 他人反馈:`同事反馈吃不了辣`、`妈妈说喜欢`

**改造技巧**:把"反馈型"信号改写成"操作型"信号——
- 「差评隔音差」→「第二次没再订那家,改订别家并加勾了『隔音好』筛选」(换店+改筛选)
- 「吃后血糖升高」→「把糖醋排骨退掉换成清蒸」(退菜+换单)
- 「红眼被吵睡不好」→「红眼航班值机都选了靠走道」(条件化选座)
- 「上夜班作息乱」→「这周第一单都在下午一两点点早餐」(下单时间分布)
- 「同事吃不了辣投诉」→「再给团队点时多数菜改成不辣」(团队订单的操作转变)

### 2.3 事件来源:不止本 App,也包括用户的数字痕迹;约束要从具体记录里提取

GUI agent 能读到的不只是它在某个 App 里的操作,还包括用户的其它数字记录。约束/事实(过敏、宗教、关系、住址等)应来自这些**具体原始记录**,由 Agent 自己提取,**不要写成已经提炼好的结构化字段**(那等于把答案直接给它)。

- ❌ 抽象字段:`忌口里标了花生过敏`、`某朋友是清真`、`健康档案填了三高`
- ✅ 具体来源(Agent 自己提取):
  - 微信聊天记录:`小李发过「我对花生过敏,上次误吃了进医院」`
  - 通讯录备注:`老马的备注是「老马 · 回民,不吃猪肉」`
  - App 内退单理由 / 订单备注:`退单理由写「我海鲜过敏」`
  - 日历日程:`后天日程「探望刘总(领导),术后恢复」`

经验:**用户本人**的约束多来自 App 内备注/退单理由;**他人**(同行的朋友/客户/家人)的约束多来自微信聊天或通讯录备注。常见来源:本 App 操作历史、退单/订单备注、微信聊天、通讯录备注、日历、地址簿。

## 3. 场景(scenario)

三个主场景,数量大致均分:

- `旅游` —— 机票/酒店/高铁/租车/接送机/行程景点/民宿/旅行中餐厅等
- `购物` —— 服装鞋帽/生鲜食品/数码/美妆护肤/家居/母婴/宠物/礼物/日用复购等
- `外卖` —— 正餐/饮品咖啡/早餐夜宵/健康减脂/多人聚餐/给家人点/商超代购/病号餐等

## 4. 难度分层(difficulty)

- **L1 直接复用**:单条清晰事件,选择可直接套用到新任务。
- **L2 泛化 / 去冗余 / 单跳推断**:从具体选择泛化到品类;多条冗余事件归纳出偏好;从行为(取消/退货/改签/差评)反推隐式偏好。
- **L3 推理 / 冲突 / 排除 / 综合**:解决事件间冲突、判断事件是否适用(含干扰项)、多事件综合、正负偏好分离、时间/季节/状态变化、个人偏好 vs 群体/安全约束。
- **L4 硬核**:在 L3 基础上再上一阶——长事件序列去噪、近因 vs 频率的权衡、二阶推断(从行为模式反推人生事件)、跨域迁移(一个域的事件作用于另一域)、言行矛盾(说的 vs 做的)、无完美解的权衡取舍、指代消歧、理解偏好背后的原因(原偏好目的失效)、兼容性/生态约束、从踩坑中纠错、区分可被临时意图覆盖的偏好 vs 不可破的硬约束。

## 5. 问题类型(problem_types,可多标签)

- `直接复用` 直接套用历史选择
- `去冗余` 多条重复/相似事件,需归纳、按频率/近因加权
- `冲突` 事件间矛盾,需解决
- `泛化` 从具体项推广到品类/属性
- `隐式推断` 从行为(取消、退货、改签、投诉、差评)反推偏好
- `多事件综合` 需组合 2~3 条事件才能得出答案
- `适用性判断` 含干扰项,或当前场景与历史不同,需判断该不该用(甚至判断都不适用)
- `正负偏好分离` 同一段经历里既有喜欢的点也有讨厌的点,要分别处理
- `时间状态变化` 季节/状态/人生阶段变了,要相应调整
- `约束优先` 安全(过敏)、健康、宗教、预算、群体包容性等硬约束优先于个人口味偏好
- `负样本` 事件与当前任务无可迁移信号(跨域无关/代买/特例/主体非本人/信息不足),正确做法是**不使用任何事件**,走通用默认,防止过度个性化
- `多跳推理` 答案不在任何单条事件里,需把 2~3 条事件串成证据链才能推出(如:搬家→更新住址→再应用就近偏好)
- `需澄清` 信息不足或过期,正确做法是主动询问而非武断臆断

L4 引入的更高阶类型:
- `二阶推断` 从一组行为模式反推出一个未明说的人生事件/状态(如怀孕、搬家、换工作),再据此行动
- `长序列去噪` 事件很多且含无关噪声,需先筛出相关再判断
- `近因vs频率` 历史高频选择与近期稳定转变冲突,需判断哪个为准(通常近期稳定转变 + 明确理由 > 历史高频)
- `跨域迁移` 一个域(如外卖)的事件,作用于另一个域(如旅游订餐)的决策
- `言行矛盾` 用户口头诉求与历史揭示性行为相反,需在尊重当前指令的前提下用行为修正
- `权衡取舍` 多个目标无法同时满足、无完美解,需按重要性排序并说明取舍
- `指代消歧` 「老地方」「老规矩」等个人化指代,需用历史指代解析,再校验当前可达性
- `偏好溯因` 理解偏好背后的真实诉求(如靠窗为看景),当场景使该诉求失效时调整
- `兼容性约束` 从已购主设备推断出生态/接口约束(如相机卡口),后续购买必须满足
- `纠错规避` 从一次踩坑(误机、误食、闲置)中学习,主动规避同类错误
- `关系推断` 从情境推断对象关系(领导/朋友/家人),据此把握分寸尺度
- `跨应用上下文` 约束/事实来自其它 App(微信聊天、通讯录备注、日历),需 Agent 跨应用读取并从原始记录里提取

## 6. 冲突解决策略(conflict resolution,L3 关键子维度)

当事件矛盾时,正确策略可能是:

- **按场景匹配**:选与当前任务上下文匹配的那次(出差 vs 私人、给自己 vs 送人、一人 vs 多人)。
- **按时间近因**:偏好随时间变化(消费升级、开始健康饮食),用最近的。
- **按频率**:高频选择 > 一次性的偶然选择。
- **按显式声明**:用户当前指令里明确表达的意图,覆盖长期偏好(如「今天想放纵吃炸鸡」)。
- **按约束优先**:过敏/宗教/健康/预算/群体包容 > 个人口味偏好。

## 7. 数据格式(testset_v2.json)

JSON 数组,每条字段:

```json
{
  "id": 1,
  "scenario": "旅游 | 购物 | 外卖",
  "difficulty": "L1 | L2 | L3 | L4",
  "problem_types": ["直接复用", "冲突", "..."],
  "instruction": "用户新指令(把当前场景上下文自然地写进指令里)",
  "events": [
    { "time": "2025-10", "event": "过去做过的任务/交互记录" }
  ],
  "expected_behavior": "Agent 应执行的具体行为(选择/筛选/排除)",
  "reasoning": "为什么这么做——如何从事件推出",
  "test_point": "本条考察点"
}
```
